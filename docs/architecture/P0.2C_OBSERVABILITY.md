# Kiến trúc P0.2C — Log và ảnh chụp tài nguyên

## 1. Phạm vi đã triển khai

P0.2C bổ sung khả năng đọc log gần nhất và một ảnh chụp tài nguyên của App A/App B. Dữ liệu đi qua đúng ranh giới quyền đã có từ P0.2B:

```text
Dashboard
    |
    | session cookie
    v
Control API
    |
    | appId + giới hạn số dòng + secret nội bộ
    v
Deployment Runner
    |
    | Docker Engine API qua Unix socket
    +--> /containers/:id/logs
    `--> /containers/:id/stats?stream=false&one-shot=true
```

Dashboard và Control API không được gắn Docker socket. Runner tiếp tục chỉ tìm container có đủ nhãn dự án Compose, service và `io.mini-paas.managed=true`; người gọi không thể truyền container ID tùy ý.

## 2. Lựa chọn thiết kế

- Dùng **ảnh chụp theo yêu cầu** thay vì gọi Docker stats trong chu kỳ làm mới danh sách ứng dụng. Docker phải lấy hai mẫu CPU để tính tỷ lệ, vì vậy gọi tự động cho mọi app mỗi 5 giây sẽ tạo tải nền không cần thiết.
- Chỉ trả 50, 100 hoặc 200 dòng trên giao diện; API chấp nhận số nguyên từ 1 đến 200.
- Runner chặn dữ liệu log thô vượt 2 MiB và rút mỗi dòng còn tối đa 4.096 ký tự trước khi trả về.
- Kết quả stats và log được tải song song nhưng có trạng thái lỗi độc lập. Container dừng vẫn có thể đọc log cũ, còn stats trả `409 container_not_running`.
- Kết quả cũ bị xóa khi đổi ứng dụng; số thứ tự yêu cầu ngăn phản hồi chậm của lần trước ghi đè lựa chọn mới.
- P0.2C không lưu stats vào SQLite. Prometheus/Grafana ở P1 sẽ đảm nhiệm chuỗi thời gian và đồ thị.

## 3. Hợp đồng API

### API qua Gateway

| Method | Endpoint | Xác thực | Giới hạn |
|---|---|---:|---|
| GET | `/api/v1/applications/:appId/logs?tail=N` | Session quản trị | `1 <= N <= 200`, mặc định 100 |
| GET | `/api/v1/applications/:appId/stats` | Session quản trị | Một mẫu cho một ứng dụng |

### API nội bộ của Runner

| Method | Endpoint | Xác thực | Mục đích |
|---|---|---:|---|
| GET | `/v1/apps/:appId/logs?tail=N` | `x-runner-token` | Đọc stdout/stderr của container được quản lý |
| GET | `/v1/apps/:appId/stats` | `x-runner-token` | Đọc một mẫu tài nguyên Docker |

Gateway không định tuyến trực tiếp đến Runner. Hai endpoint công khai kiểm tra session, ứng dụng có trong SQLite và schema đầu vào trước khi gọi Runner.

## 4. Dữ liệu trả về

Mỗi dòng log gồm thời gian do Docker gắn, luồng `stdout` hoặc `stderr` và nội dung. Runner loại mã điều khiển ANSI và che một số mẫu phổ biến như `password`, `token`, `secret`, `authorization`, `api_key`. Đây chỉ là lớp phòng vệ bổ sung, không bảo đảm phát hiện mọi bí mật; ứng dụng vẫn phải tránh ghi dữ liệu nhạy cảm vào log.

Ảnh chụp tài nguyên gồm:

- `cpuPercent`: tỷ lệ CPU tính từ chênh lệch `cpu_stats` và `precpu_stats`, có nhân số CPU trực tuyến.
- `memoryWorkingSetBytes`: bộ nhớ dùng trừ `inactive_file`, gần với working set hơn giá trị usage thô.
- `memoryLimitBytes` và `memoryPercent`: giới hạn container và tỷ lệ working set trên giới hạn.
- `pids`: số tiến trình hiện có trong container.
- `networkRxBytes`, `networkTxBytes`: tổng byte nhận/gửi trên các interface kể từ khi container khởi động.
- `sampledAt`: thời điểm Docker tạo mẫu.

Các chỉ số này mô tả một thời điểm hoặc bộ đếm tích lũy; chúng không thay thế hệ thống lưu chuỗi thời gian.

## 5. Trạng thái giao diện

Dashboard có vùng **Log và tài nguyên container** sau danh sách ứng dụng. Người quản trị có thể:

1. Chọn App A hoặc App B.
2. Chọn 50, 100 hoặc 200 dòng log.
3. Làm mới dữ liệu theo yêu cầu.
4. Xem CPU, RAM, PID, lưu lượng mạng và thời điểm lấy mẫu.
5. Cuộn vùng log bằng bàn phím hoặc con trỏ mà không làm trang bị tràn ngang.

Giao diện đã được kiểm tra ở 1440×900, 768×1024 và 390×844. Ở mobile, bốn thẻ tài nguyên chuyển thành một cột, điều khiển vẫn hiện đầy đủ và vùng bấm chính cao tối thiểu 44 px.

## 7. Giới hạn

- Docker stats snapshot không cho biết xu hướng, đỉnh tải hay p95; P1 cần Prometheus/cAdvisor cho mục đích đó.
- Log lấy từ driver hiện tại của Docker trên một host; chưa có lưu trữ log tập trung hoặc tìm kiếm toàn văn.
- Bộ che bí mật dùng biểu thức mẫu và không thể thay thế chính sách log an toàn.
- Quyền đọc log/stats vẫn đi qua Runner có Docker socket; nếu Runner bị chiếm quyền, host vẫn có rủi ro cao.
- Bộ đếm mạng tích lũy từ lúc container chạy và trở về đầu khi container được thay thế.
- Số liệu trên Docker Desktop/OrbStack có thể khác Linux trực tiếp, đặc biệt ở cách hạch toán bộ nhớ và lớp máy ảo.
