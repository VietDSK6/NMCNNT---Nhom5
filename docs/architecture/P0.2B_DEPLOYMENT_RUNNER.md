# Kiến trúc P0.2B — Deployment Runner và vòng đời ứng dụng

## 1. Phạm vi đã triển khai

P0.2B bổ sung khả năng đọc trạng thái container và thực hiện bốn thao tác có kiểm soát: `start`, `stop`, `restart`, `update`. Quyền truy cập Docker không được đưa vào Dashboard hoặc Control API mà nằm trong một dịch vụ riêng là Deployment Runner.

```text
Trình duyệt
    |
    v
Nginx Gateway :8080
    |
    +--> Dashboard
    +--> Control API --> SQLite
    |         |
    |         `-- appId + action + version --> Deployment Runner
    |                                             |
    |                                      /var/run/docker.sock
    |                                             |
    |                                         Docker Engine
    |
    `--> App A / App B qua mạng edge
```

Dashboard và Control API ở mạng `control`. App A và App B ở mạng `edge`. Gateway là thành phần duy nhất tham gia cả hai mạng và là dịch vụ duy nhất mở cổng ra máy phát triển. Runner chỉ ở mạng `control`, không công khai cổng host.

## 2. Ranh giới quyền

| Thành phần | Docker socket | Lệnh tùy ý | Cổng host | Vai trò |
|---|---:|---:|---:|---|
| Dashboard | Không | Không | Không | Gửi thao tác qua API |
| Control API | Không | Không | Không | Xác thực, kiểm tra dữ liệu, lưu operation/audit |
| Deployment Runner | Có | Không | Không | Gọi Docker Engine API theo danh sách cho phép |
| Gateway | Không | Không | `127.0.0.1:8080` | Định tuyến HTTP |
| App A, App B | Không | Không | Không | Ứng dụng mẫu |

Docker socket tương đương một quyền rất cao trên máy chạy Docker. Các tùy chọn `read_only`, `cap_drop` hay `no-new-privileges` không làm socket trở nên an toàn. Vì vậy biện pháp chính là thu hẹp bề mặt Runner:

- Runner không có endpoint chạy shell hoặc nhận tên container/image tùy ý.
- Chỉ nhận `app-a`, `app-b` và bốn action đã khai báo.
- Phiên bản chỉ lấy từ catalog cố định: App A có `v1.0.0`, `v2.0.0`; App B có `v1.0.0`.
- Runner chỉ tìm container có đồng thời nhãn dự án Compose, tên service và `io.mini-paas.managed=true`.
- Control API gọi Runner bằng secret riêng trong mạng nội bộ.
- Mỗi ứng dụng chỉ có tối đa một operation ở trạng thái `queued` hoặc `running`.

Đây là giới hạn phù hợp cho mô hình lab một người quản trị; chưa phải sandbox để chạy mã nguồn của người dùng bên ngoài.

## 3. Luồng operation

```text
Dashboard -> POST action -> Control API
                           1. kiểm tra session/origin/schema
                           2. tạo operation = queued trong SQLite
                           3. trả HTTP 202
                           4. chuyển operation = running
                           5. gọi Runner nội bộ
                           6. lưu succeeded/failed và audit
Dashboard <- polling GET applications + operations
```

Migration SQLite số 2 thêm bảng `operations`, gồm ứng dụng, action, phiên bản đích, người yêu cầu, trạng thái, thông báo và các mốc thời gian. Partial unique index ngăn hai operation hoạt động đồng thời trên cùng ứng dụng. Runner cũng có khóa trong bộ nhớ theo `appId` để bảo vệ lớp đặc quyền nếu có yêu cầu bỏ qua API.

## 4. Hợp đồng API

### API công khai qua Gateway

| Method | Endpoint | Kết quả |
|---|---|---|
| GET | `/api/v1/applications` | Health HTTP, runtime container, phiên bản và operation đang chạy |
| POST | `/api/v1/applications/:appId/actions` | Xếp hàng action, trả `202 Accepted` |
| GET | `/api/v1/operations?limit=N` | Lịch sử operation, tối đa 100 bản ghi |
| GET | `/api/v1/audit-events?limit=N` | Nhật ký kết quả quản trị |

Body action hợp lệ:

```json
{ "action": "restart" }
```

```json
{ "action": "update", "version": "v2.0.0" }
```

### API nội bộ của Runner

| Method | Endpoint | Mục đích |
|---|---|---|
| GET | `/health` | Health check nội bộ |
| GET | `/v1/apps/:appId` | Đọc trạng thái container được quản lý |
| POST | `/v1/apps/:appId/actions` | Thực hiện action đã cho phép |

Các endpoint `/v1/*` yêu cầu header secret; Gateway không định tuyến tới Runner.

## 5. Quy trình cập nhật phiên bản

Ảnh App A v1 và v2 được build trước bằng `make up`. Khi cập nhật, Runner:

1. Kiểm tra phiên bản đích trong catalog và ảnh tương ứng có thật trên Docker Engine.
2. Inspect container hiện tại và dừng container nếu đang chạy.
3. Đổi tên container cũ thành bản dự phòng tạm thời.
4. Tạo container mới bằng cấu hình mạng, health check, giới hạn tài nguyên và nhãn quản lý cố định.
5. Khởi động và chờ health của container mới đạt `healthy`.
6. Chỉ xóa container cũ sau khi bản mới khỏe.
7. Nếu bước tạo/khởi động/health thất bại, xóa bản mới, đổi lại tên và khởi động container cũ.

Cơ chế ở bước 7 là phục hồi khi thao tác cập nhật lỗi, không được quảng bá là tính năng rollback lịch sử phiên bản hoàn chỉnh. P0.2B chưa lưu nhiều release hay cung cấp nút rollback riêng.

## 6. DNS và trạng thái dừng

Container update làm thay đổi địa chỉ IP nội bộ. Gateway dùng DNS `127.0.0.11` của Docker với upstream `resolve` để cập nhật địa chỉ mà không cần khởi động lại Nginx. Timeout kết nối/đọc được giới hạn để một app đã dừng trả lỗi 502 hoặc 504 trong thời gian hữu hạn thay vì treo request lâu.

Dashboard hiển thị riêng:

- `runtime.status`: trạng thái container do Runner đọc từ Docker.
- `health.status`: kết quả HTTP đi qua Gateway.
- `desiredVersion`: phiên bản mong muốn trong SQLite.
- `observedVersion`: phiên bản ứng dụng tự báo qua HTTP.

## 8. Giới hạn

- Runner gắn Docker socket nên nếu Runner bị chiếm quyền, host Docker vẫn có rủi ro rất cao.
- Secret nội bộ là cơ chế phù hợp cho lab một host, chưa phải quản lý định danh dịch vụ cấp sản xuất.
- Operation chạy bất đồng bộ trong tiến trình Control API; chưa có hàng đợi bền vững để tự tiếp tục sau khi API bị dừng đột ngột.
- Khóa Runner nằm trong bộ nhớ và mô hình chỉ chạy một bản sao Runner.
- `update` chỉ dùng ảnh đã build sẵn, không nhận repository hoặc build mã tùy ý.
- Toàn bộ hệ thống vẫn có điểm lỗi đơn ở host, Docker Engine, Gateway, API, Runner và SQLite.
